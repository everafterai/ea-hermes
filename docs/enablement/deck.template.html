The one thing to leave with

Every automation is four blocks

Trigger

What sets it off. Someone posts, someone asks, or a schedule fires.

Context

What it's allowed to look at. A channel, a database, a folder, the public web.

Judgment

The thinking part. Read, classify, compare, decide, draft.

Action

What it does about it. Post, file, draft, update, flag, notify.

If you can say — when X happens, go look at Y, work out Z, then do W — it's automatable.

And if you can't say it yet, that's useful too. It means one of the four blocks is missing — almost always the trigger.

Is this a good first automation?

All three have to be yes

Weekly?

Does it happen at least once a week? Automating something quarterly is a hobby project.

Annoying?

Is it low-judgment grind — the kind of thing you'd hand to a sharp new hire?

85% enough?

If it's mostly right, is it still useful? If only perfect will do, pick something else first.

What it's good at, and what it isn't

Strong

  • Reading far more than a person has time to read
  • Doing the same careful thing every time, without drift
  • Watching things nobody has been assigned to watch
  • Getting a first draft to 80% in seconds
  • Sorting a messy stream of anything into categories

Not strong

  • Anything where being quietly wrong is expensive — pricing, contracts, money out the door
  • Work with no clear trigger, that happens "when it happens"
  • Judgment that depends on context nobody wrote down
  • Things rare enough that you'd forget it exists
  • Being the last check before something reaches a customer
Before you start having ideas

What it can see,
and what it can't

Access is granted by role — and we keep it narrow on purpose

  • A role is a named list of tools. Not a seniority level. Today we run admin, operator, marketing and readonly.
  • It doesn't roam. It works in the conversation it's been invited into, with the tools its role holds. It is not reading the company in the background.
  • Every squad gets a written scope card — exactly which channel, which database, which folder.
  • Nothing customer-facing goes out unreviewed. Drafting is the job. Sending stays with a person.

The first design question isn't what would I love to give it.
It's what is the least information this could possibly need?

An automation that needs a trust decision waits on a conversation. An automation built on public information and one output channel ships this week. Start outside the walls, and earn your way in.

If your squad is stuck

Support

  • "Has this been reported before?" before anything is filed
  • First-response draft from known issues and docs
  • Weekly digest clustering reports into themes
  • Escalation watcher: critical, open past 24 hours

Product

  • Monthly roll-up clustering feature requests by theme
  • Competitor release watch from public changelogs
  • Spec companion drafting a PRD skeleton from a thread
  • What customers asked for vs what we shipped

R&D

  • Release notes drafted from merged pull requests
  • Stale PR nudge to whoever's sitting on it
  • Incident context pack: every related past issue
  • Dependency and CVE watch on public advisories
