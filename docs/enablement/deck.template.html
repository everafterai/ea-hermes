The one thing to leave with

Every automation is four blocks

Trigger

What sets it off. Someone posts, someone asks, or a schedule fires.

Context

What it's allowed to look at. A channel, a database, a folder, the public web.

Decision

The part that works something out. Either rules you write down, or judgment you can only describe.

Action

What it does about it. Post, file, draft, update, flag, notify.

If you can say — when X happens, go look at Y, work out Z, then do W — it's automatable.

And if you can't say it yet, that's useful too. It means one of the four blocks is missing — almost always the trigger.

Before you assume everything needs a model

Two kinds of automation — and half of them don't think at all

Six of our eight live automations are both at once: a script does the gathering, an agent handles the one part that needed judgment.

Scripts

The rule is something you can write down. Scan Jira for tickets sitting in "ready to deploy", find who owns them, nudge them. No reasoning involved — just steps, run reliably, on time, forever.

Agents

You can't write the rule down, only describe what good looks like. Is this message a bug report? Is this news worth anyone's attention? Turn this thread into a decision record.

ScriptAgent
Decides byRules you can stateJudgment you can only describe
Same input twiceIdentical answer, alwaysUsually the same. Not guaranteed
Costs per runEffectively nothingReal, if small
When it's wrongIt breaks loudlyIt can be quietly plausible

Can you write the rule down? It's a script.
Can you only describe what good looks like? It needs judgment.

Most real automations are both. The skill is splitting the idea into the part you can write down and the small part you can't — then giving the agent only the second piece.

Same instinct as the access rule. Least information, least judgment. Every bit of either that you hand over is a bit more that can drift.

If it's just a script, why not write it yourself?

Because the script was never the hard part

What used to stop you

  • Getting Jira, GitHub and Slack to talk to each other
  • Somewhere to keep the credentials
  • A machine to run it on, at 9am, every day
  • Knowing when it silently stopped working
  • Knowing Python

What you do now

  • Describe it. It writes it.
  • It already holds the connections
  • It owns the schedule
  • It tells you when it breaks
  • You change it by asking, in English
Is this a good first automation?

All three have to be yes

Weekly?

Does it happen at least once a week? Automating something quarterly is a hobby project.

Annoying?

Is it low-judgment grind — the kind of thing you'd hand to a sharp new hire?

85% enough?

For judgment-based ones: if it's mostly right, is it still useful? If it has to be exact every time, make it a script instead.

What it's good at, and what it isn't

Strong

  • Reading far more than a person has time to read
  • Doing the same careful thing every time, without drift
  • Watching things nobody has been assigned to watch
  • Getting a first draft to 80% in seconds
  • Sorting a messy stream of anything into categories

Not strong

  • Anything where being quietly wrong is expensive — pricing, contracts, money out the door. Make that a script.
  • Work with no clear trigger, that happens "when it happens"
  • Judgment that depends on context nobody wrote down
  • Things rare enough that you'd forget it exists
  • Being the last check before something reaches a customer
Before you start having ideas

What it can see,
and what it can't

Access is granted by role — and we keep it narrow on purpose

  • A role is a named list of tools. Not a seniority level. Today we run admin, operator, marketing and readonly.
  • It doesn't roam. It works in the conversation it's been invited into, with the tools its role holds. It is not reading the company in the background.
  • Every squad gets a written scope card — exactly which channel, which database, which folder.
  • Nothing customer-facing goes out unreviewed. Drafting is the job. Sending stays with a person.

The first design question isn't what would I love to give it.
It's what is the least information this could possibly need?

An automation that needs a trust decision waits on a conversation. An automation built on public information and one output channel ships this week. Start outside the walls, and earn your way in.

  • Write six scope cards, one per squad

  • Create #radar
